## A. 它是什么、会不会害我

### 1. 它会不会让我的正常请求更容易失败？

不会 —— 前提是默认配置。理由：

- 五条规则里有两条（`chunk` 分片洪水、`noOutput` 慢速渗流）都带**「产出为 0」这个必要条件**：模型只要真的在出正文或调工具，它们**绝不插手**，不管思考了多久。
- `stall`（卡住不动）只在「一个分片都不来」时命中，默认 3 分钟。
- `repeat`（输出退化重复）只在「一段窗口里行数远多于唯一行数」时命中，正常叙述每行都不一样。
- 全语料重放（340 个真实会话、41,808,459 字符）：命中 222 次，**全部落在两个已知退化的会话里**，其它会话**一次都没被碰过**。

**唯一需要你主动关注的是 `noOutputMs`（默认 10 分钟）**：如果你确实有「合法地思考十分钟以上才吐第一个字」的用法，请调大它。

### 2. 它会修改模型的输出吗？

**不会。** 触发之前到达的每一个数据块都**原样透传**：同一个对象引用，不改写、不丢弃、不重排。它做的只有两件事：

1. 在判定命中时**停止向上游取值**，并向下游吐一个终结块（错误码 `LOOP_GUARD`）；
2. 把这个失败码接管下来，限制重试次数。

### 3. 那它到底改变了什么？

只改变**失败之后的处理方式**：

| | 没有守卫 | 有守卫 |
|---|---|---|
| 一次循环尝试 | 一直跑到上游自己报错（1–5 分钟，甚至几小时） | 在判定命中时立刻掐断（默认最快 3 分钟，`repeat` 可到 1–2 千字符） |
| 失败之后 | 宿主按默认策略再重试 5 次 | 允许 `maxGuardedRetries`（默认 1）次**纠正重试**，之后终结 |
| 重试时 | 原样重发 | 把 `reasoningEffort` 降一档（默认开） |

真机实测过完整链路：一次「5,450 个推理分片 / 260 秒 / 零产出」的尝试被掐断，**1 次**纠正重试后 73 秒，该步正常产出并收尾。

### 4. 它能治好模型的循环吗？

**不能。** 循环是上游模型的退化行为，DSH 侧能做的只是「尽早掐断 + 一次纠正重试 + 降一档推理档位」。真正的产出恢复取决于模型下一次尝试是否正常。**它的价值是止损，不是修复。**

### 5. 它会拖慢模型吗？

它的开销只在本地 CPU（统计与判定），实测每 1000 字符输出约 **3.25 ms**（默认窗口）、真实流分片粒度下约 **3.34 ms**。相比一次卡死几十分钟到几小时，这个量级可以忽略。

（对比：修复前在真实分片粒度下是 **106 ms / 1000 字符**，大窗口下是 **307 ms / 1000 字符** —— 这两个数字是历史值，当前版本已修掉。）

## B. 装上之后

### 6. 设置页在哪？看不到怎么办？

`设置` → 左侧导航 **「循环守卫」**（每 5 秒自动刷新一次）。

看不到的话，按顺序检查：

1. **装完有没有重启宿主** —— 必须重启一次，否则浏览器半区进不了 boot graph（宿主的扫描是增量的，否定结论缓存到进程重启）。
2. 重启后**刷新浏览器页面**。
3. 你的环境里有没有 `webServer` 服务 —— **没有它就没有任何设置页**（但守卫照常工作）。

### 7. 装了之后我什么都没感觉到，是不是没生效？

「没感觉到」通常是**正常的** —— 它只在那四种坏形态出现时才动手。要确认它在跑，用这两招：

```bash
curl -s http://127.0.0.1:<宿主端口>/loop-guard/state
```

1. 看 `value.enabled` 是不是 `true`；
2. **随便发一轮对话，再查一次，看 `stats.attempts` 有没有变大** —— 变大就说明监听真的挂上了（本机实测：几分钟内从 69 涨到 81）。

### 8. 为什么 `guarded` 一直是 0？

因为**它只在真的出现那四种坏形态时才加一**。`attempts` 在涨、`guarded` 是 0，含义是「守卫在正常工作，而你的会话很健康」。

想主动验证一次判定链路，见 [INSTALL.md](INSTALL.md) §4.3（临时把 `stallTimeoutMs` 调到 10 秒，做完记得改回来）。

### 9. 我改了配置为什么不生效？

四种可能，逐条对：

| 原因 | 说明 |
|---|---|
| 改的是 `settingsPath` / `maxRecent` / `debug` | **这三个在界面里改不了**，只能写在 `cordis.patch.yml` 里 |
| 你直接改了设置文件 | 设置文件**只在插件挂载时读一次**，运行中改它没用。请用设置页，或重启宿主 |
| 你改的是 `cordis.patch.yml` | 那一行不会自动重载（hmr 没有监听目录）。要重载：`set_plugin target="include:loop-guard" enabled=false` 再 `=true`，或重启宿主 |
| 写盘失败了 | 保存失败**只告警不抛错**（设计如此，避免把宿主弄崩）。查宿主日志 |

### 10. 统计为什么突然清零了？

三种情况：

1. 有人点了设置页的**「清零」**（等价于 `POST /loop-guard/reset`）；
2. **宿主重启了** —— 统计只在内存里，不落盘；
3. 守卫那一行被重载过（重载 = 重新挂载）。

配置值不受影响：那 13 个可改键是写盘的。

### 11. 「省下的时间」准吗？

**是估算，不是实测。** 算法：每次触发时按「这次尝试本来还会跑到 `attemptBudgetMs`（默认 30 分钟）」算差值再求和；`absolute` 那条已经跑满预算，按 0 计（不虚报）。

所以它是一个**量级参考**，不是「我实测省了多少墙钟时间」。README 里给的「`chunk` 档约 4.9 分钟命中」同样是**按速率推算**的。

### 12. 为什么「重试时降低推理档位」看不到效果？

因为**降档只对广告了推理档位的模型有效**，而且只在最近 **120 秒**内循环过的 agent 上生效。当前档位不在 `max / high / low / off` 这个阶梯里时，它**是空操作**（宁可不降，也不瞎猜档位名）。这不算失败，是设计取舍。

### 13. 能不能只开某一条规则？

**不能单独开关**，但可以等效地关掉某一条：

| 想关掉的规则 | 等效做法 |
|---|---|
| `chunk`（分片洪水） | `reasoningChunkLimit` 调到很大 |
| `stall`（卡住不动） | `stallTimeoutMs` 调到很大 |
| `noOutput`（慢速渗流） | `noOutputMs` 调到很大（比如大于 `attemptBudgetMs`） |
| `repeat`（输出退化重复） | `repeatMinChars` 设成等于 `repeatWindowChars` 只退回旧语义；要基本关掉就把 `repeatUniqueRatio` / `repeatGramRatio` 调到最小、`repeatCycles` / `repeatMinLines` 调到最大 |
| `absolute`（30 分钟兜底） | `attemptBudgetMs` 调到很大 |

想**全部**关掉：`enabled: false`（一条监听都不装）。

> 注意一个边界：如果把 `noOutputMs` 配得比 `attemptBudgetMs` 还大，零产出的尝试仍会被 `noOutput` 抢先标名，`byRule` 里就少记一次 `absolute`。**只影响统计标签，不影响中止本身。**

### 14. 多开宿主 / 多个 profile 会互相影响吗？

**会共用同一份设置文件。** 设置文件的路径只按 `$DSH_HOME` 定位，与 profile 无关。

具体表现：A 实例在设置页保存的值会写进那个文件，但**不会立刻影响已经在运行的 B 实例**（文件只在挂载时读一次）。两边各自写盘时会互相覆盖。

本机实测到过一次：文件里是 `repeatMinChars: 500`，而运行中的实例通过 `/state` 报的是 `1000`。**不是 bug，是机制。** 想让两边一致就重启宿主（重启后以文件为准）。

### 15. 支持哪些 provider / 模型？

判定逻辑**完全不依赖 provider**：它只看 DSH 已公开的三个事件（`llm/stream`、`agent/request-error`、`agent/request`）和数据块本身，不碰任何适配器内部实现。

唯一的 provider 相关性是**降档**（`lowerEffortOnRetry`）：模型/网关不广告推理档位时，降档是空操作。

### 16. 内部调用（压缩会话、生成标题等）会不会被误掐？

它们的正常输出是**文本**，所以 `chunk` 和 `noOutput` 都不会命中（两条都要求「产出为 0」）。

残余风险照实说：如果某次压缩**合法地**零产出超过 10 分钟，会被 `noOutput` 掐掉。观测数据里零产出调用最长 **3.39 分钟**，没有这种用例。

### 17. 卸载后有什么残留？

| 残留 | 位置 |
|---|---|
| 设置文件 | `$DSH_HOME/loop-guard-settings.json`（`DSH_HOME` 未设 → `~/.dsh/loop-guard-settings.json`） |
| profile 里的那一行 | `remove_bundle` 会处理 |
| 统计 | **无残留**（只在内存里） |

想彻底干净：`remove_bundle` + 删掉那个 JSON + 重启宿主。

### 18. 它会不会动我的其它插件 / 我的数据？

不会。它只做三件事：包住 LLM 流逐块统计、接管**自己产生的** `LOOP_GUARD` 失败码、在重试时降一档推理档位。它不写任何会话数据、不碰别的插件、统计也不落盘。

### 19. 我手改设置文件、写坏了会怎样？会不会把插件弄挂？

**不会弄挂。** 设置文件是「宽进」的：**里面写什么都不会让插件挂载失败**，设置页一定打得开（这样你永远有界面手段自救）。实测（源码快照 `index.js` `d3041377d613d1c8` / v0.5.1）：

| 你在文件里写了什么 | 会怎样 |
|---|---|
| 数值越界（`reasoningChunkLimit: 50`、`maxGuardedRetries: 99`、`repeatUniqueRatio: 5`） | 该值被忽略，**退回 `cordis.patch.yml` 里的值**，并打一条告警 |
| 不是整数（`repeatCycles: 6.5`） | 同上 |
| `repeatMinChars` > **生效窗口** | **夹紧到窗口大小** + 告警 |
| `repeatMinChars` 比**出厂默认窗口 6000** 大、但没超过**生效窗口**（例如你在 yml 里把窗口调到 30000，再从设置页把门槛调到 20000） | **正常生效，无告警** —— 判越界看的是**生效窗口**，不是默认的 6000 |
| 坏 JSON / 内容不是对象 | **告警** + 忽略整个文件（退回 yml 的值） |
| 不认识的键、类型写错（数字写成字符串） | **静默丢弃该键**（不告警） |

一句话：**坏值只会被「退回 yml 的值」或「夹紧到生效窗口」，不会抛错。** 唯一「抛错」的地方是 `cordis.patch.yml`（那是你手写的正式配置，写错就该报错）。

> 想知道到底哪条键被退回了：看宿主日志里那条 `dsh-loop-guard: 设置文件里的 XXX 不合法，已退回 yml 的值：…`（夹紧的那条文案是 `…已夹紧到窗口大小`）。详见 [CONFIG.md](CONFIG.md) §5.1。
