# dsh-loop-guard

**推理循环守卫** —— 模型陷入「只出思考、不出结果」的死循环、或者整条流卡住不动、或者在重复同一小段文本时，提前掐断**这一次尝试**，并止住把它反复重试的风暴。

一句话：**把一次本来要卡几十分钟到几小时的会话，压缩成几秒钟的一次干净中止。**

## 1. 它解决什么现象

用户报的是三句话：**「对话无限重复」「卡会话」「一个子会话运行时间过长」**。

查会话日志查到的根因是同一个：

```
模型陷入推理循环 / 流卡死
  → 这次尝试以错误收场
  → 宿主按默认重试策略把它再试 5 次（同一次确定性失败）
  → 但每次尝试本身要跑 1–5 分钟，甚至几小时
  → 会话卡死数十分钟到数小时；子会话整个时间预算被烧光后被杀，零产出
```

**重试把一次本来几秒就能判定的失败，放大成了几十分钟到几小时的卡死。**

三个真实案例（都取自本机会话日志）：

| 案例 | 现象 | 实测数字 | 来源 |
|---|---|---|---|
| 子会话 `aa01cb95` | 同一步重试 5 次，每次都只出思考、不出文本 | 5 次尝试分别产出 **20,704 / 16,902 / 3,163 / 21,103 / 11,827** 个推理分片，**文本分片 0 个**；整步 **18.2 分钟**，会话 **18.4 分钟**被杀；重试退避 522 / 1001 / 1949 / 3850 / 7259 ms | `_loop-guard-rootcause-main.txt` |
| 主会话 `session-c502a332` | 某一步耗时 **3.48 小时** | 6 次尝试里 5 次推理分片为 **0**，时间戳之间是 **1.95 小时 + 1.5 小时**的「一个分片都没来」空档 | `_loop-guard-session-scan.txt` |
| 会话 `b0a019e8` | 思考里同一句话重复几千次（用户原话：「问题在思考里面」） | 单块 **85,705–102,796** 字符、非空行 5,947–7,074 行、唯一行占比 **0.5%–3.8%**、最高频行 `Let me go.` 出现 **2,931–3,332** 次 | 插件源码文件头的实测取证表 |

放大效应还有规模证据：本机扫描 **333 个会话**，其中 **37 个** `depth=1 / turn=1` 的子会话总时长**恰好 18.4 分钟**（`_loop-guard-session-scan.txt`）—— 它们撞在同一个硬顶上。

> 第三种形态（「慢速渗流」）也是真机实测到的：**5,450 个推理分片 / 260 秒 / 产出 0**，全程没有任何 ≥180 秒的空档 —— 只盯「分片数量」或「有没有空档」的规则都抓不到它（`_loop-guard-report.md`）。

## 2. 它拦哪几类问题

**四种坏形态，五条规则**（第 5 条是兜底天花板，不是一种「形态」）。任一命中就掐断，优先级从上到下：

| # | 规则 | 坏形态 | 判据（源码 `detectTrip` 的真实条件） | 默认阈值 |
|---|---|---|---|---|
| 1 | `chunk` | **分片洪水**：一直在思考，一个字的正文都不出 | 推理分片数 **≥ `reasoningChunkLimit`** 且 产出分片 **= 0** | 20,000 片 |
| 2 | `stall` | **卡住不动**：一个分片都不来 | 距上一个分片（**或起始时刻**，即首块之前也算）**≥ `stallTimeoutMs`** | 180,000 ms（3 分钟） |
| 3 | `noOutput` | **慢速渗流**：分片慢慢来，但一直不出结果 | 已耗时 **≥ `noOutputMs`** 且 产出分片 **= 0** | 600,000 ms（10 分钟） |
| 4 | `repeat`（行判据） | **输出退化重复**：在重复同一小段文本 | 窗口 **≥ `repeatMinChars`**，且某个子窗内：非空行数 **≥ `repeatMinLines`**、唯一行占比 **≤ `repeatUniqueRatio`**、最高频那一行出现次数 **≥ `repeatCycles`** | 1,000 字符 / 30 行 / 0.2 / 6 次 |
| 4 | `repeat`（片段兜底） | 同上，但整块**几乎只有一行**（行判据结构上抓不到） | 窗口 **≥ `repeatMinChars`**，且整窗非空行数 **< `repeatMinLines`**，且最坏子窗的 8 字符不重叠片段唯一率 **≤ `repeatGramRatio`** | 0.10 |
| 5 | `absolute` | 兜底：任何单次尝试都不该跑这么久 | 已耗时 **≥ `attemptBudgetMs`**（**不看产出**） | 1,800,000 ms（30 分钟） |

两个关键定义：

- **产出分片 = `text-delta` + `tool-call-delta`**。`reasoning-delta`（思考）**不算产出**。
- **窗口 = 最近 `repeatWindowChars`（默认 6000）个字符**，只吃推理分片与文本分片（工具调用分片不参与）。判据不是看整个窗口，而是在窗口上枚举若干**子窗**（尺度 = `repeatMinChars` × 2^k，再加上窗口本身），取**最坏的那个值** —— 这样「前半段正常、后半段开始循环」也不会被前面的正常内容稀释掉。

**防误杀设计（这是本插件最重要的取舍）：**

| 规则 | 会不会误杀「正常的长回答 / 长思考」 | 为什么 |
|---|---|---|
| `chunk` | 不会 | 带「产出为 0」这个必要条件 —— 只要模型真的在出正文或调工具，它绝不插手，不管思考了多久 |
| `noOutput` | **这是五条里最可能误杀的一条** | 同样要求「产出为 0」，所以「合法地思考超过 10 分钟才吐第一个字」会被它掐掉。默认给到 600 秒，实测没有这种用例（见 §3.2），**如果你确实有超长思考的正常请求，优先调大它** |
| `stall` | 基本不会 | 沉默就是沉默，有没有出过文本都拦。默认 3 分钟，离实测的 1.95 小时空档有两个数量级余量 |
| `repeat` | 不会（但有边界） | 只在「行数远多于唯一行数」时命中，正常叙述每行都不一样。边界是「常量模板 + 只变计数器」这种形状，余量只有 1.06×（见 §3.2） |
| `absolute` | 可能 | 不看产出，跑到 30 分钟无条件切断 —— 这是故意的最后兜底 |

### 触发之后会发生什么

| 步骤 | 行为 |
|---|---|
| ① 掐断 | 立刻**停止向上游取值**，向下游吐一个终结块：`{type:'finish', reason:{kind:'error', failure:{code:'LOOP_GUARD', message:'…'}}}`。触发之前已经到达的每个块**原样透传** |
| ② 止住重试风暴 | 失败码 `LOOP_GUARD` 回到宿主重试层时，本插件**只认自己这个码**：同一个 `turn/step` 允许 `maxGuardedRetries` 次（默认 **1**）纠正重试，之后返回「终结」—— 不再把同一次循环重试 5 遍。**其它任何失败码（网络超时、传输错误……）一律交给默认策略，绝不干预** |
| ③ 给它一条走得通的路 | 最近 120 秒内循环过的 agent，下一次请求把 `reasoningEffort` 降一档（`max → high → low → off`）。当前档位不在这个阶梯里时是空操作（宁可不降，也不瞎猜档位名） |

**真机验证过这条链路**（`_loop-guard-report.md`，带时间戳）：

```
22:18:23  step/start
22:18:27  起连续 5,450 个推理分片、产出 0
22:22:43  守卫触发，注入 finish{failure.code:'LOOP_GUARD'}（已耗时 260 秒）
          失败到达重试层 → 守卫放行 1 次纠正重试（retriesAllowed=1）
22:23:56  该步正常产出 reasoning + text + tool-call + tool-call，step 正常收尾，后续 step 继续
```

也就是说：一次空转 4.3 分钟、零产出的尝试被拦下，**一次**纠正重试就恢复了正常产出。

> 口径说明：这一次是**早期版本**用一条更激进的规则（「已耗时 ≥ 240 秒且产出为 0」）拦下的；那条规则后来被删掉了，因为它会误杀「先长时间思考、再开始作答」的正常请求。它在这里的价值是**证明了整条链路可用**（掐断 → 纠正重试 → 恢复正常产出）。

## 3. 能提升什么（实测数字）

### 3.1 省下的等待时间

| 场景 | 现状（没有守卫） | 有守卫 | 口径 |
|---|---|---|---|
| 分片洪水（`aa01cb95` 那一类） | 整步 **18.2 分钟**、73,699 个推理分片、0 个文本分片，5 次重试全部白烧，最后撞 18.4 分钟硬顶被杀 | `chunk` 档按**整步平均速率推算**约 **4.9 分钟**命中（20,000 片 ÷ 约 67 片/秒） | 实测总量 + **推算**触发点 |
| 输出退化重复（`b0a019e8` 那一类） | 只能等模型自己停（跑到 max-tokens）或被用户手动中止；单块 85,705–102,796 字符 | 全语料里 7 个真退化短块的**实际触发点**是 **1,024（3 个）/ 1,536 / 2,048（2 个）/ 2,560** 字符处（块长 2,029–4,521） | 实测（`_verify-repeat-corpus-v55.log`） |
| 卡住不动（`c502a332` 那一类） | 1.95 小时 + 1.5 小时的零分片空档 | `stall` 档 **3 分钟**命中 | 实测空档 + 阈值 |

界面上「省下的时间」这个数字是**估算**：每次触发时按「这次尝试本来还会跑到 `attemptBudgetMs`（30 分钟）」算差值再求和（`absolute` 那条已跑满预算，按 0 计，不虚报）。它**不是**实测省下的墙钟时间。

- 语料里 **0 误杀**是真的；

## 5. 快速上手

**默认值可以直接用。** 装完重启就行，不需要改任何配置：

- 五条规则的默认阈值都来自实测（见 §6 的「默认值的来历」），全语料 **0 误杀**；
- 唯一的例外是 **`noOutputMs`（10 分钟）**：如果你**确实**有「正常地思考十分钟以上才吐第一个字」的用法，把它调大（比如 900000 = 15 分钟），或者调到很大等于关掉这一档；
- 界面上改完点**保存**即刻生效，并且**重启后仍然记得**（写进设置文件）。

三条「不要踩」的：

| 别踩 | 为什么 |
|---|---|
| 别把 `repeatGramRatio` 往上调 | 它一调高就更容易误杀**长单行自然语言**：实测中文自然散文单行约 **0.36**、英文约 **0.45**，而真退化单行只有 **0.007–0.009**。默认 0.10 |
| 别把 `stallTimeoutMs` / `noOutputMs` / `attemptBudgetMs` 调到 10000 以下 | 在 `cordis.patch.yml` 里会被配置校验直接拒绝（抛错并点名）；在设置页里会被本地拦下（不发请求）；在设置文件里会被**忽略并退回 yml 的值 + 告警**（见 §6.4） |
| 别在 `cordis.patch.yml` 里写不存在的键 | 未知键**直接抛错**，会让这一行加载失败（不静默兜底） |

## 6. 配置项

### 6.1 完整表

「界面可改」= 能在设置页里改、并且会被写盘记住。共 **13 个**：总开关 + 11 个阈值 + 降档开关。剩下 3 个只能写在 `cordis.patch.yml` 里。

| 键 | 类型 | 默认值 | 取值范围 | 界面可改 | 什么时候该动它 |
|---|---|---|---|---|---|
| `enabled` | boolean | `true` | `true` / `false` | ✅ | 想彻底关掉守卫（一条监听都不装，完全不干预）时设为 `false` |
| `reasoningChunkLimit` | number | `20000` | 整数 ≥ `100` | ✅ | 抓「分片洪水」的灵敏度。调小=更早掐断（更激进）；调大=更宽容 |
| `stallTimeoutMs` | number | `180000`（3 分钟） | 整数 ≥ `10000` | ✅ | 抓「一个分片都不来」。**调小**：网络慢/长排队时可能误杀；**调大**：真卡死时等更久 |
| `noOutputMs` | number | `600000`（10 分钟） | 整数 ≥ `10000` | ✅ | 抓「慢慢来但一直不出结果」。**五条里最可能误杀的一条**：有超长思考的正常请求就**调大**它 |
| `repeatWindowChars` | number | `6000` | 整数 `1000`–`200000` | ✅ | 重复检测的观察窗口。**调大**：能发现更长的循环周期，但 CPU 开销上升、判定更迟；**调小**：更快更省，但长周期循环可能看不出来 |
| `repeatMinChars` | number | `1000` | 整数 `500`–`repeatWindowChars` | ✅ | 判据的最低字符门槛（窗口短于它就不判）。**设成等于 `repeatWindowChars` = 退回旧语义（只判满窗）**，这是「灵敏度回退」开关 |
| `repeatMinLines` | number | `30` | 整数 `5`–`5000` | ✅ | 窗口里最少要有多少非空行。**调大**：只抓「很多行在重复」；**调小**：单行/少行退化更容易走片段兜底 |
| `repeatCycles` | number | `6` | 整数 `2`–`100` | ✅ | 最高频那一行至少要重复几次。**调小**=更早判定；**调大**=要重复更多轮才算 |
| `repeatUniqueRatio` | number | `0.2` | `0.01`–`0.9` | ✅ | 唯一行占比上限。**调大**=更激进（更容易命中）；**调小**=更保守 |
| `repeatGramRatio` | number | `0.10` | `0.01`–`0.9` | ✅ | 单行/少行退化的片段唯一率上限。**调高会更容易误杀长单行自然语言**（见 §5） |
| `attemptBudgetMs` | number | `1800000`（30 分钟） | 整数 ≥ `10000` | ✅ | 绝对天花板，不看产出。**调小**：长任务会被切断（实测有一条一直在正常出文本的长流会在 12 分钟处被切）；**调大**：真循环的兜底时间变长 |
| `maxGuardedRetries` | number | `1` | 整数 `0`–`5` | ✅ | 掐断后允许宿主再纠正重试几次。`0` = 拦到就终结；调大 = 多给几次机会（但每次都可能再烧时间） |
| `lowerEffortOnRetry` | boolean | `true` | `true` / `false` | ✅ | 纠正重试时是否把推理档位降一档。关掉它就没有第 ③ 道防线 |
| `settingsPath` | string | `''`（空） | 绝对或相对路径 | ❌ 只能写 yml | 想换设置文件的落盘位置时填；留空 = `$DSH_HOME/loop-guard-settings.json` |
| `maxRecent` | number | `50` | 整数 `1`–`500` | ❌ 只能写 yml | 设置页「最近触发」保留多少条 |
| `debug` | boolean | `false` | `true` / `false` | ❌ 只能写 yml | 排障：把每次拦截写进宿主日志 |

### 6.2 默认值的来历（都不是拍脑袋）

| 键 | 默认值怎么来的 |
|---|---|
| `reasoningChunkLimit: 20000` | 实测的循环尝试是 20,704 / 21,103 / 16,902 / 11,827 个推理分片 —— 取 20000 能拦住最大的几次，同时给正常长推理留余量 |
| `stallTimeoutMs: 180000` | 实测的零分片空档是 1.95 小时与 1.5 小时，3 分钟离它们有两个数量级余量，又远大于正常的 token 间隔 |
| `noOutputMs: 600000` | 实测那次渗流是 5,450 片 / 260 秒；真实调用时长分布里「有产出且 ≥600 秒」**0 次**、零产出调用最长 3.39 分钟 → 600 秒高于全部观测样本（余量 1.34×） |
| `attemptBudgetMs: 1800000` | 更小的值（4 分钟、12 分钟）实测会切断**一直在正常出文本**的长流，所以放宽到 30 分钟，只当最后兜底 |
| `repeatWindowChars: 6000` | 实测退化块里最高频行出现 2,931–3,332 次、唯一行占比 0.5%–3.8% —— 6000 字符足够看出「同一小段在循环」，又不会把正常散文卷进来 |
| `repeatMinChars: 1000` | 旧前置是「窗口必须满 6000」，导致块长 < 6000 的 7 个真退化短块**永远不判**。改成 1000 后全语料命中从 24 涨到 216 且误杀仍为 0 |
| `repeatMinLines: 30` / `repeatCycles: 6` / `repeatUniqueRatio: 0.2` | 由真实退化块的形态定：唯一行占比 0.5%–3.8%（阈值 0.2 对最近的误杀有 1.29× 余量）；`repeatCycles` 从旧判据「行数 ≥ 轮数 × 唯一行数」改成「最高频那一行 ≥ 轮数」，因为旧判据会真漏检一条 376 行 / 占比 32.4% / `Let me go.` × 233 的真实退化块 |
| `repeatGramRatio: 0.10` | 从 0.35 降下来的：0.35 会误杀长单行自然语言（中文散文单行 0.3613，只剩 3% 余量），而两个真退化单行只有 0.0067 / 0.0093 |

### 6.3 配置的三层，谁覆盖谁

| 层 | 位置 | 生效时机 | 优先级 |
|---|---|---|---|
| ① bundle 补丁 | 包内 `cordis.patch.yml` 的 `config:` | 宿主启动 / 该行重载时 | 最低 |
| ② 设置文件 | `$DSH_HOME/loop-guard-settings.json`（`DSH_HOME` 未设时是 `~/.dsh/...`） | **只在插件挂载时读一次** | 覆盖 ① |
| ③ 设置页 / `POST /loop-guard/config` | 内存 + 原子写回 ② | 立即 | 覆盖 ① ② |

三条由此推出的使用规则：

- **界面里改过的值，重启后仍然生效** —— 因为文件优先于 yml。
- **想回到 yml 的值**：删掉那个设置文件，再重启宿主。
- **运行中直接改设置文件没有用** —— 文件只在挂载时读一次。要么用设置页，要么重启宿主。

### 6.4 校验规则

| 情况 | 结果 |
|---|---|
| `cordis.patch.yml` 里写了不存在的键 | **抛错并点名**（`未知的 config 键 "xxx"（可用：…）`），这一行加载失败 |
| `cordis.patch.yml` 里类型不对 | 抛错：`必须是 boolean` / `必须是有限数字` / `必须是 string` |
| `cordis.patch.yml` 里数字越界 | 抛错并给出范围，例如 `config.reasoningChunkLimit 必须 >= 100` |
| `cordis.patch.yml` 里 `repeatMinChars > repeatWindowChars` | 抛错 |
| 设置页里填了非法值 | **只在本页提示，不发请求**（11 条针对性文案，中英双语） |
| 接口 `POST /loop-guard/config` 收到未知键 / 类型错 / 越界 | `400` + `unknown-key` / `bad-type` / `bad-range` |
| **设置文件**里单键数值越界或不是整数 | **忽略该值 → 退回 `cordis.patch.yml` 的值，并打一条告警**（不抛错，插件照常挂载） |
| **设置文件**里 `repeatMinChars > repeatWindowChars`（跨字段，**合并后**判定） | **夹紧到窗口大小 + 告警**。**两条路径都走这里**：① 单键本身越界（门槛 20000 而生效窗口只有 6000）；② 单键各自合法但合起来越界（门槛 5000 + 窗口 4000）。**判越界看的是「生效窗口」，不是出厂默认的 6000** —— 所以「yml 把窗口调到 30000、你从设置页把门槛调到 20000」是**合法**的，会正常生效（详细表见 [docs/CONFIG.md](docs/CONFIG.md) §5.1-B） |
| **设置文件**是坏 JSON / 内容不是对象 | **告警** + 忽略整个文件（退回 `cordis.patch.yml` 的值） |
| **设置文件**里有不认识的键 / 类型不对 | **静默丢弃该键**（不告警） |

> 最后四行是**实测**结果（真 `apply()` + 桩上下文 + **临时**设置文件；源码快照 `index.js` `d3041377d613d1c8` / v0.5.1，20 组用例）。
> 一句话：**设置文件里写什么都不会让插件挂载失败**，设置页一定打得开；坏值只会被「退回 yml 的值」或「夹紧到生效窗口」并留一条告警（**一个坏键一条告警**，且只有一个 `dsh-loop-guard: ` 前缀）。

## 9. 已知限制

照实写，不修饰：

| # | 限制 |
|---|---|
| 1 | **它治不好模型的循环，只能快速止损。** 循环是上游模型的退化行为；本插件做的是「尽早掐断 + 一次纠正重试 + 降一档推理档位」。真正的产出恢复取决于模型下一次尝试是否正常 |
| 2 | **它不能保证一定解开卡死的上游连接。** 上游彻底挂住时，`iterator.return()` 未必能打断那个挂起的 `next()`（取决于适配器实现）。保证的是**下游不会再被吊住**：超时那一刻已经吐了终结块并结束自己的流 |
| 3 | **`noOutputMs` 是五条里最可能误杀的一条。** 余量只有 1.34×（600 ÷ 449 秒）。有超长思考的正常用法请调大 |
| 4 | **`repeat` 的灵敏度在 v0.5 提高了。** 「常量模板 + 只变计数器」这种形状的余量只剩 **1.06×**，且子窗有 ±30% 相位噪声。要退回旧语义就把 `repeatMinChars` 设成等于 `repeatWindowChars` |
| 5 | **全部命中都来自两个会话。** 语料里 222 次命中只落在 `c3e13580`（216）与 `1997d29e`（6）两个会话上，证据强度受这两个会话的多样性限制 |
| 6 | **统计不落盘。** 只放内存：宿主重启、或点「清零」，统计就归零。只有那 13 个可改配置项会写盘 |
| 7 | **`absolute`（30 分钟）对「一直在正常出文本的超长任务」是硬切。** 观测数据里有产出的调用最长 7.48 分钟、没有 ≥30 分钟的，但这是观测上界，不是保证 |
| 8 | **内部调用（压缩会话、生成标题等）同样受约束。** 它们的正常输出是文本（产出 > 0），所以 `chunk` / `noOutput` 不会命中；但若某次压缩合法地零产出超过 10 分钟会被掐（观测里零产出调用最长 3.39 分钟） |
| 9 | **降档只对广告了推理档位的模型有效。** 当前档位不在 `off/low/high/max` 阶梯里时是空操作（宁可不降，也不瞎猜） |
| 10 | **多开宿主会共用同一份设置文件。** 设置文件按 `$DSH_HOME` 定位、与 profile 无关；而且**只在挂载时读一次**。所以 A 实例保存的设置不会立刻影响已在运行的 B 实例，两者各自写盘、互相覆盖（本机实测到过一次：文件里 `repeatMinChars` 是 500，而运行中的实例内存里仍是 1000） |

## 11. 未验证项

| # | 未验证的事 | 现状 |
